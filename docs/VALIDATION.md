# 화면·서버 유효성 검사

입력을 받는 기능은 **화면에서 실수를 빠르게 안내하고, 서버에서 요청을 다시 검사**합니다. 브라우저 검사는 우회할 수 있으므로 서버 검사를 생략할 수 없습니다. 단순 문구·색상 변경처럼 입력과 무관한 작업에는 검증 코드를 새로 추가할 필요가 없습니다.

이 문서는 개발 기준입니다. 현재 보일러플레이트는 Zod를 환경 변수 검증에 사용하며 React Hook Form과 resolvers는 설치 구성에 포함하지만, 회원가입·CRUD 폼과 해당 서버 검증은 아직 구현되어 있지 않습니다.

## 어디에서 무엇을 검사하나요?

| 위치                      | 목적                               | 예시                                                 |
| ------------------------- | ---------------------------------- | ---------------------------------------------------- |
| 프론트엔드: 브라우저 화면 | 입력 실수를 즉시 안내              | 필수 입력, 이메일 형식, 글자 수·숫자 범위            |
| 백엔드: 서버 진입점       | 우회·조작·잘못된 요청 차단         | 형식·범위 재검사, 허용 필드, 경로·검색 매개변수 검사 |
| 서버 업무·권한 처리       | 실제 처리 가능 여부 확인           | 로그인·본인 자료 여부, 중복 가입, 예약 가능 여부     |
| DB 제약과 동시성 처리     | 동시에 요청해도 데이터 무결성 유지 | 고유 이메일·관계 제약, 원자적 재고 감소·트랜잭션     |

유효한 이메일 형식이라는 것과 이메일 소유를 확인했다는 것은 다릅니다. 로그인 여부와 자료 수정 권한도 별개입니다. 회원가입의 선택 사항은 [인증 안내](AUTHENTICATION.md)를 참고하세요.

## 기존 도구 활용

| 도구                  | 역할                                             |
| --------------------- | ------------------------------------------------ |
| `react-hook-form`     | 폼 입력 상태·제출·오류 표시 관리                 |
| `zod`                 | 실행 중 실제 입력값의 형식·범위 검사             |
| `@hookform/resolvers` | 화면의 React Hook Form과 Zod 연결                |
| Prisma와 PostgreSQL   | 데이터 저장, 고유·관계 제약과 필요한 동시성 처리 |

이 도구들은 기존 `package.json`에 포함되어 있으므로 새 검증 라이브러리를 반드시 설치할 필요는 없습니다. Next.js도 서버 폼 입력에 Zod 등의 검증을 적용하는 방법을 안내합니다. [Next.js 폼 안내](https://nextjs.org/docs/app/guides/forms)

## 권장 처리 흐름

```text
입력 규칙 결정 → 화면 검사·안내 → 서버에서 실제 입력 재검사
→ 업무·권한 확인 → 안전한 DB 처리 → 결과·오류를 화면에 표시
```

로그인·권한 확인과 입력 검사의 세부 순서는 정보 노출과 기능 요구에 맞춰 정합니다. 어느 경우든 데이터 변경 전에 필요한 검사를 완료해야 합니다.

### 1. 입력 규칙부터 정하기

필수·선택 항목, 형식, 길이·범위, 허용 값과 공백·빈값 처리 방침을 정합니다. 숫자 입력이나 FormData는 문자열일 수 있고 빈 문자열·누락·null은 서로 다를 수 있습니다. 무조건 숫자로 변환해 빈값을 0으로 받거나 시간대 없는 날짜를 임의로 해석하지 않도록 합니다. 비밀번호는 사용자가 입력한 값을 임의로 trim하거나 변환하지 않습니다.

### 2. 화면에서 빠르게 안내하기

필드 옆에 이해하기 쉬운 오류를 표시하고 label과 연결합니다. 제출 중 표시·중복 제출 방지를 제공하되 버튼 비활성화가 서버의 중복 처리 방지를 대신하지는 않습니다. 사용자가 브라우저 검사를 우회해도 서버가 잘못된 요청을 거절해야 합니다.

### 3. Server Action·REST API에서 재검사하기

Server Action 인자·FormData, Route Handler의 JSON 본문, 경로·검색 매개변수는 모두 외부 입력입니다. 파싱·검증을 거쳐 성공한 값만 처리합니다. 잘못된 JSON 등 파싱 실패도 안전하게 처리해야 합니다. TypeScript 타입 선언만으로 실제 요청이 검사되지는 않습니다.

같은 형식 규칙은 작은 공통 Zod 스키마로 공유할 수 있습니다. 다만 공유 파일에 DB 코드·비밀값·서버 전용 모듈을 넣으면 안 됩니다. 서버에서만 가능한 중복 조회·권한 판정·업무 처리는 별도로 유지합니다. 폴더를 일괄 생성하거나 모든 검사를 한 파일에 모을 필요는 없습니다.

허용된 필드로 저장할 값을 명시적으로 구성합니다. 요청 객체 전체를 DB에 그대로 넘기지 마세요. 소유자 ID·역할·가격 등은 세션·서버의 신뢰할 수 있는 데이터로 결정하거나 해당 값을 바꿀 권한을 확인해야 합니다.

### 4. 서버 규칙과 DB 안전성 확인하기

이메일 중복을 미리 조회해도 동시에 가입하면 두 요청이 모두 통과할 수 있습니다. 필요한 고유 제약을 유지하고 저장 시 충돌을 안전한 결과로 처리해야 합니다. 예약·재고는 단순 사전 조회나 트랜잭션 사용만으로 충분하다고 가정하지 말고 제약·원자적 갱신·격리 수준 등 기능에 맞는 방식을 검토합니다. [Prisma 트랜잭션 안내](https://docs.prisma.io/docs/orm/v7/prisma-client/queries/transactions)

Prisma 스키마에 제약이 적혀 있어도 실제 DB에 반영됐는지는 별도 확인이 필요합니다. 제약 추가·마이그레이션·실제 데이터 변경은 승인 범위에서 진행합니다.

### 5. 서버 결과를 화면에 연결하기

형식 오류는 필드별로, 처리 불가 등은 폼 전체 안내로 표시할 수 있습니다. 서버가 반환한 예상 가능한 실패를 React Hook Form의 `setError` 등에 연결하고 사용자에게 수정할 내용을 알려 주세요. 기존 API 응답 형식을 임의로 변경하지 않습니다. [React Hook Form 서버 오류 연결](https://react-hook-form.com/advanced-usage)

예상하지 못한 오류는 화면에 안전한 안내를 제공하고 서버에서 추적합니다. 비밀번호·토큰·입력 본문·DB 오류 객체 전체를 화면이나 로그에 남기지 않습니다. 가입·로그인·계정 복구에서는 회원 존재 여부를 과도하게 노출하지 않도록 오류 문구도 검토합니다. 확인 위치는 [오류 추적 안내](TROUBLESHOOTING.md)를 참고하세요.

## 비개발자가 확인할 항목

- 올바른 값을 넣으면 정상 처리되는가?
- 필수 항목 누락·형식 오류·최소/최대 경계값에 화면 안내가 있는가?
- 브라우저 검사를 우회하거나 타입·추가 필드를 바꾼 요청도 서버에서 처리 방침에 맞게 거절·무시하는가?
- 로그인하지 않았거나 다른 회원의 자료를 바꾸려는 요청을 서버가 막는가?
- 중복·동시 요청에서 필요한 DB 규칙과 업무 조건이 유지되는가?
- 예상 가능한 오류는 화면에 표시되고 예기치 않은 오류는 안전하게 추적되는가?

우회 요청·동시성 검사에서 실제 데이터가 변경될 수 있으므로 승인된 테스트 환경과 범위에서 진행합니다. 실제로 실행하지 않은 항목은 미검증으로 기록하세요. `npm run check`는 타입·린트·서식 검사이며 실제 입력 우회·권한·동시 요청 검증을 대신하지 않습니다.

```text
필드별·폼 전체 오류 안내와 경계값·브라우저 검사 우회·동시 요청의 검증 계획을 제시해 주세요.

```

관련 계획에는 검사 위치와 실제 결과·미검증 범위를 남깁니다. [계획 양식](../plans/README.md), [개발 지침](../.agent/server.md#화면서버-유효성-검사)을 함께 참고하세요.
