# 페이지 오류 확인과 전달

사용자는 화면의 안내로 문제를 이해하고, 에이전트는 관련 코드와 로그를 확인해 원인을 분석합니다. 터미널만 확인하거나 페이지마다 별도의 오류 안내 코드를 붙일 필요는 없습니다. 이 문서는 공통 확인 절차이며 오류 수집 프로그램이나 서버 기능을 추가하지 않습니다.

현재 보일러플레이트에는 로그인·CRUD 예제 기능이 없습니다. 아래 내용은 앞으로 Server Action·REST API 등의 기능을 만들 때도 활용할 수 있는 기준입니다. 기본 실행은 [설치 안내](SETUP.md), DB 연결은 [Supabase 안내](SUPABASE_SETUP.md), 배포는 [Vercel 안내](VERCEL_DEPLOYMENT.md)를 참고하세요.

## 어디를 먼저 보나요?

| 오류 상황                                 | 먼저 확인할 곳                          | 함께 확인할 내용                                        |
| ----------------------------------------- | --------------------------------------- | ------------------------------------------------------- |
| 입력 검증·중복 예약 등 예상 가능한 실패   | 화면의 입력 오류·결과 메시지            | 서버 반환 결과가 화면에 연결되는지                      |
| 로컬 Server Action 처리 실패              | `npm run dev`를 실행한 터미널           | 화면 메시지, Network의 요청과 결과                      |
| REST API 호출 실패                        | 브라우저 Network                        | 요청 경로·메서드·상태 코드·안전한 응답 내용과 서버 로그 |
| 화면 이벤트·브라우저 렌더링 오류          | 브라우저 Console                        | 오류 발생 전 조작, 관련 호출 코드                       |
| Server Component 렌더링·직접 DB 조회 실패 | 개발 서버 터미널 또는 배포 서버 로그    | 해당 페이지의 서버 코드와 DB·외부 서비스 처리           |
| 배포된 페이지의 서버 처리 실패            | 해당 Vercel 배포의 Runtime Logs         | 발생 시각·페이지 경로·요청 정보                         |
| 빌드·배포 실패                            | 로컬 빌드 터미널 또는 Vercel Build Logs | 처음 발생한 관련 오류와 명령                            |

Server Action도 브라우저에서 서버에 요청하므로 Network에서 요청 실패를 확인할 수 있습니다. 다만 일반 REST API의 JSON 응답과 같은 형식이라고 가정하지 마세요. Server Component가 서버에서 직접 조회한 데이터는 브라우저 Network에 별도 API 요청으로 나타나지 않을 수 있습니다.

## 1. 로컬에서 개발 중이라면

### 개발 서버 터미널

`npm run dev`를 실행하고 계속 켜 둔 터미널을 확인합니다. 서버에서 발생한 오류·로그와 관련 파일·줄 번호가 표시될 수 있습니다. 여러 서버를 실행했다면 브라우저 주소의 포트와 해당 터미널이 같은 앱인지 확인하세요.

모든 오류가 자동 기록되는 것은 아닙니다. 코드가 오류를 잡고 결과로 반환했다면 터미널에 아무것도 없을 수 있습니다. 로그가 없다고 정상이라는 뜻은 아니며 화면과 서버의 반환 처리도 확인해야 합니다.

### 브라우저 Console·Network

브라우저 개발자 도구를 열고 다음을 확인합니다. Windows에서는 보통 F12 또는 Ctrl+Shift+I로 열 수 있습니다.

1. **Console:** 화면 코드·이벤트 처리 오류와 관련 메시지를 확인합니다. 일부 개발용 서버 메시지가 보일 수 있어도 서버 로그 전체를 대신하지는 않습니다.
2. **Network:** 도구를 연 상태에서 오류가 발생한 조작을 확인하고 해당 요청을 찾습니다. URL·메서드·상태 코드, Preview 또는 Response의 안전한 부분을 확인합니다.
3. 개발 서버 터미널에서 같은 시점의 서버 로그와 비교합니다.

저장·예약·가입·결제 같은 조작을 반복하면 실제 데이터가 다시 변경될 수 있습니다. 무작정 재시도하거나 Network의 요청 재전송 기능을 사용하지 말고, 재현에 데이터 변경이 필요하면 승인된 테스트 환경과 범위를 확인하세요.

## 2. Server Action과 REST API의 차이

### Server Action

입력 검증·업무상 거절은 구조화된 결과로 돌려주고 화면에 표시하도록 구현할 수 있습니다. 예상하지 못한 서버 오류는 서버 로그에서 원인을 추적하고 화면에는 안전한 메시지를 제공합니다. Next.js는 예상 가능한 실패와 예외를 구분해 처리하도록 안내합니다. [Next.js 오류 처리](https://nextjs.org/docs/app/getting-started/error-handling)

HTTP 요청이 성공했더라도 반환 결과가 업무상 실패일 수 있습니다. Network 상태 코드만 보지 말고 화면·반환 결과·서버 로그를 함께 확인하세요. 배포 환경에서는 상세 서버 오류가 브라우저에 제공되지 않을 수 있으며, 화면에 digest 같은 식별자가 있으면 발생 시각과 함께 서버 로그 대조에 활용합니다. 서버 오류 원문을 브라우저에 공개하도록 바꾸지 않습니다.

### REST API 또는 외부 API

같은 앱의 REST API는 보통 `src/app/api/.../route.ts` 같은 Route Handler에서 처리하지만 실제 호출 경로를 코드에서 확인해야 합니다. 모든 페이지가 API를 호출하거나 이 폴더에 처리 코드가 있다고 가정하지 않습니다.

상태 코드는 원인 후보를 좁히는 단서입니다. 400은 입력 문제, 401은 인증 문제, 403은 권한 문제, 404는 경로·대상 부재, 500번대는 서버·상위 서비스 문제 등을 먼저 살펴볼 수 있지만 코드별 실제 의미는 구현과 응답을 확인해야 합니다. `fetch`는 4xx·5xx 응답만으로 항상 예외를 던지지 않으므로 `response.ok` 등 실패 응답을 처리하는지도 확인합니다.

브라우저에서 직접 호출한 외부 API는 Network에 나타납니다. Server Action이나 Route Handler 내부에서 외부 API를 호출했다면 브라우저에는 앱 요청만 보일 수 있으므로 서버 코드와 로그를 추가로 확인합니다.

## 3. Vercel에 배포했다면

Vercel 대시보드에서 해당 프로젝트와 문제가 발생한 배포를 선택합니다. 실행 중 서버 오류는 **Logs / Runtime Logs**, 배포 과정의 실패는 **Build Logs**를 확인합니다. 로컬 터미널에는 Vercel에서 실행된 서버 로그가 자동 표시되지 않습니다. [Vercel Runtime Logs 안내](https://vercel.com/docs/logs/runtime)

Preview인지 Production인지, 어느 배포 주소에서 발생했는지, 발생 시각과 시간대를 함께 확인하세요. 로그 검색 범위·보존 기간·접근 권한에 따라 기록이 보이지 않을 수 있습니다. 로그를 찾지 못한 것과 오류가 없었던 것은 구분해야 합니다. 현재 실제 배포가 없다면 이 단계는 미검증으로 남기면 됩니다.

## 4. 에이전트에 전달할 정보

- 오류가 발생한 페이지 경로와 실행 환경: 로컬 dev / 로컬 build·start / Vercel Preview·Production.
- 어떤 버튼·입력을 사용했는지, 기대한 결과와 실제 결과.
- 발생 시각과 시간대, 비밀값을 가린 화면·Console·관련 서버 오류 구간.
- 확인 가능한 경우 요청 메서드·경로·상태 코드와 안전한 응답 메시지 또는 오류 식별자.
- 최근 관련 변경과 반복 발생 여부. 이미 수행한 검사는 결과와 함께 전달.

Server Action인지 REST API인지 모르면 페이지 경로와 조작만 알려 주세요. 에이전트가 코드를 확인해 호출 방식을 추적할 수 있습니다. 에이전트는 별도로 실행한 터미널·브라우저·Vercel 계정에 자동으로 접근할 수 있는 것은 아니며, 확인할 수 없는 로그는 필요한 부분만 요청할 수 있습니다.

비밀번호·토큰·쿠키·Authorization 헤더·DB 연결 URL·실제 개인정보는 제외하세요. `.env`, 요청 본문 전체, 전체 Network 기록이나 HAR 파일을 그대로 공유하지 마세요. URL의 검색 매개변수와 오류 메시지 안에도 비밀값이 있을 수 있습니다.

```text
[페이지 경로]에서 [조작]하면 [오류 현상]이 발생합니다.
실행 환경은 [로컬 dev / Vercel Preview 등]이고,
발생 시각은 [시각과 시간대]입니다.
Server Action·REST API·직접 조회 중 어떤 경로인지 코드에서 확인하고,
관련 로그에 접근할 수 있으면 함께 대조해 원인 후보와 분석 순서를 알려 주세요.
접근할 수 없는 로그는 필요한 부분만 요청해 주세요.
아직 파일 수정·설치·DB 변경·배포는 진행하지 마세요.
```

## 5. 수정 후 확인

원인과 변경안을 확인한 뒤 필요한 범위만 승인합니다. 관련 실패 조건과 정상 흐름, 사용자 화면의 안전한 안내를 확인하고 변경 범위에 맞게 타입·린트·서식·빌드를 검사합니다. 정적 검사를 통과했다고 실제 DB 처리나 Vercel 동작까지 검증된 것은 아닙니다.

로그 추가·오류 화면 구현도 파일 변경에 해당합니다. 인증·권한·TLS 검증을 끄거나 캐시 설정을 임의로 바꿔 오류를 숨기지 않습니다. 실제 DB 쓰기·마이그레이션·배포와 요청 재전송은 승인된 대상·범위에서만 수행합니다. 결과에는 확인된 원인·변경 내용·실제 검증과 남은 확인 사항을 구분해 남깁니다.

에이전트의 상세 기준은 [페이지·서버 오류 추적 지침](../.agent/troubleshooting.md#페이지서버-오류-추적), 작업 승인 절차는 [Codex 안내](CODEX_GUIDE.md)를 참고하세요.
