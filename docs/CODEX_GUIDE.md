# Codex와 함께 작업하기

Codex에서 이 프로젝트 폴더를 열고 원하는 작업을 한국어로 요청하세요. 현재 상태를 설명하고 원하는 결과를 구체적으로 알려주면 됩니다.

## 처음 요청하기

다음처럼 분석이나 계획부터 요청할 수 있습니다.

> 이 프로젝트의 구조와 실행 방법을 비개발자가 이해할 수 있도록 설명해 줘.

> 회원가입 화면을 만들기 전에 필요한 작업과 변경할 파일을 보여줘. 아직 파일은 수정하지 마.

> 오류 메시지는 다음과 같아. 관련 파일을 확인하고 원인과 수정안을 설명해 줘.

오류를 전달할 때 실제 비밀키·비밀번호·DB 연결 URL·개인정보는 제외하세요.

## 새 기능을 만드는 기본 순서

데이터 저장이 필요한 새 기능은 아래 흐름으로 진행합니다. 기능별로 필요한 단계만 수행하며, 모든 요청에서 DB나 서버를 새로 만드는 것은 아닙니다.

```text
요구사항 분석·계획 → DB 분석 → 서버 처리 → 화면 구현 → 연결 검증
```

### 1. 요구사항 분석·계획

누가 쓰는 기능인지, 어떤 화면을 거쳐 어떤 결과를 얻어야 하는지 설명합니다. 화면 흐름도 이 단계에서 함께 검토합니다. Codex가 작업 범위·변경 파일·완료 기준을 제시하면 필요한 내용을 확인하고 구현 범위를 승인하세요.

> [만들고 싶은 기능]의 요구사항을 분석하고 계획을 세워 주세요. 사용 흐름, DB 필요 여부, 변경할 파일과 완료 기준을 설명해 주세요. 아직 파일은 수정하지 마세요.

여러 단계의 기능이라면 아래의 [계획 파일 안내](#계획을-파일로-남기기)에 따라 분석·승인 범위를 기록할 수 있습니다.

### 2. DB 분석

저장할 항목·관계·기존 모델을 검토합니다. DB가 필요 없거나 기존 모델로 충분하면 모델 수정은 생략합니다. Prisma 모델 파일 수정과 실제 DB 테이블 변경은 별개입니다.

> 계획한 기능에 필요한 데이터와 기존 Prisma 모델을 분석해 주세요. 변경이 필요하면 수정안과 기존 데이터에 미치는 영향을 보여 주세요. 실제 DB 변경과 마이그레이션은 별도 승인 전 실행하지 마세요.

설정·연결·개발 테이블 생성은 [Supabase DB 안내](SUPABASE_SETUP.md)를 확인하세요.

### 3. 서버 처리

입력 검증, 필요한 권한 확인, 저장·조회 처리와 오류 결과를 구현합니다. 여기서 서버 처리는 Next.js 프로젝트 안의 서버 코드를 뜻하며, 별도 서버를 반드시 만드는 것은 아닙니다.

> 승인한 계획에 따라 입력 검증·권한·DB 처리·오류 응답을 구현해 주세요. 승인 범위를 벗어나는 DB 변경이 필요하면 먼저 알려 주세요.

### 4. 화면 구현

계획에서 정한 화면·폼을 서버 처리와 연결합니다. 처리 중·성공·오류·데이터 없음 상태가 사용자에게 보이는지 확인합니다.

> 승인한 화면 흐름에 맞춰 서버와 연결되는 화면을 구현해 주세요. 입력 폼, 로딩, 성공·오류와 빈 상태를 포함하고 모바일에서도 확인해 주세요.

### 5. 연결·권한·동작 검증

화면에서 요청한 내용이 서버와 DB까지 이어지는지 확인합니다. 정상 입력뿐 아니라 잘못된 입력과 권한 없는 요청도 검토합니다. 실제 데이터 쓰기와 배포는 승인한 대상·범위 안에서 진행하고, 검사 결과와 미검증 항목을 구분하세요.

> 승인된 범위에서 화면·서버·DB 연결과 권한을 검증해 주세요. 타입·린트·서식·빌드 결과와 아직 확인하지 못한 범위를 알려 주세요. 실제 DB 쓰기와 배포는 별도 승인 범위를 확인하세요.

단순 문구·스타일 수정은 관련 단계만 수행합니다. 이미 승인한 계획 안에서는 각 단계마다 같은 승인을 반복할 필요가 없고, 새로운 DB 변경이나 범위 확대가 필요할 때 추가로 확인합니다.

### 첫 화면에서 참고하기

src/app/page.tsx는 위 순서의 설명·확인 항목·요청 예시를 보여 주는 한국어 시작 안내 화면입니다. 요청 예시를 선택해 복사한 뒤 내 기능에 맞게 바꿔 사용할 수 있습니다. 안내를 읽거나 문장을 복사하는 것만으로 파일 수정·DB 변경이 실행되지는 않습니다. 실제 서비스 제작 시 이 화면은 원하는 첫 화면으로 교체하세요.

에이전트가 따를 상세 작업 기준은 [개발 지침](../.agent/development.md#새-기능의-기본-진행-순서)에 있습니다.

## 계획을 파일로 남기기

여러 단계로 진행하는 새 기능은 요구사항·범위·검증 결과를 plans/에 남기면 대화가 길어지거나 에이전트를 다시 실행해도 작업 기준을 확인하기 쉽습니다. 단순 문구·색상 수정까지 매번 파일을 만들 필요는 없습니다.

### 어떤 작업에서 작성 여부를 확인하나요?

| 작업 상황                               | 기본 안내                                                  |
| --------------------------------------- | ---------------------------------------------------------- |
| 여러 단계·여러 파일의 새 기능           | 기록할 이유와 범위를 설명하고 작성 여부를 확인합니다.      |
| DB 모델·권한·외부 API 등 영향이 큰 변경 | 변경 영향과 승인 범위를 남길 필요성을 설명하고 확인합니다. |
| 협업·인수인계·다른 날 재개할 작업       | 기존 계획을 먼저 확인하고, 없으면 작성을 제안합니다.       |
| 관련 계획이 이미 있는 작업              | 기존 계획을 재사용하며 중복 파일 생성을 피합니다.          |
| 단순 문구·스타일 수정                   | 기본적으로 생략하고, 사용자가 원하면 작성합니다.           |

예를 들어 Codex가 “여러 파일과 DB 검토가 필요한 기능입니다. 요구사항·변경 범위·검증 결과를 plans/에 기록할까요?”라고 안내할 수 있습니다. 작성·생략 중 선택하면 됩니다. 같은 작업 범위에서 이미 결정했다면 같은 질문을 반복하지 않으며, 범위나 위험이 실질적으로 달라졌을 때 다시 설명합니다.

계획 파일을 만들지 않기로 해도 필요한 채팅 계획·승인·검증 절차는 유지합니다. 계획 파일 작성 여부를 정하는 것과 실제 구현·DB 변경·배포 승인은 별개입니다.

### 작성과 진행

1. Codex가 채팅에 계획 초안과 파일 경로를 제시합니다.
2. 작성자 식별자를 확인하고 파일 생성을 승인합니다.
3. 승인한 계획을 파일로 남긴 뒤, 별도로 확인된 구현 범위에서 진행합니다.
4. 작업을 이어 갈 때 해당 계획과 실제 코드를 확인하고 진행 상태·검증 결과를 갱신합니다.

파일명은 **YYYYMMDD-HHmmss-작성자-작업명.md**이며 KST 생성 시각을 사용합니다. 작성자는 사용자가 지정한 식별자나 확인된 요청자의 GitHub 사용자명을 사용하고, 없으면 질문합니다. package.json의 원 제작자나 Git user.name을 자동 사용하지 않습니다. 이름이 겹치면 식별자를 추가하며 기존 파일을 덮어쓰지 않습니다.

생성 후 파일명은 유지하고 수정 시각·진행 상태는 본문에서 갱신합니다. 같은 기능의 계획을 공유하면 작업을 이어 가기 쉽지만, 같은 파일을 동시에 고친 경우에는 충돌 확인이 여전히 필요합니다.

> [만들 기능]의 요구사항을 분석하고 계획 초안과 plans/ 파일 경로를 보여 주세요. 작성자 식별자는 내가 지정하거나 확인한 값을 사용하고, 모르면 먼저 물어보세요. 확인 후 파일 생성을 승인하겠습니다. 아직 파일은 생성하거나 수정하지 마세요.

계획 파일의 체크 표시를 사용자 승인이나 검증 성공으로 간주하지 마세요. 실제 DB 변경·배포·Git 작업은 승인 범위를 별도로 확인하며, 비밀번호·연결 주소·개인정보는 계획에 기록하지 않습니다. 이 보일러플레이트에는 [작성 방법과 기본 양식](../plans/README.md)만 있으며 실제 기능 계획은 미리 생성하지 않았습니다.

## 화면 재사용과 아토믹 디자인 (선택 사항)

여러 화면에서 쓰는 버튼·입력창을 각각 만들면 색상이나 동작을 바꿀 때 여러 파일을 수정해야 합니다. 공통으로 사용할 부분을 한 번 만들고 조합하면 화면의 디자인과 동작을 일관되게 유지하기 쉽습니다.

**아토믹 디자인은 작은 UI 요소를 조합해 화면을 생각하는 방법입니다.** 모든 기능을 정해진 폴더에 나눠 넣어야 한다는 뜻은 아니며, 아래 용어를 외울 필요도 없습니다.

| 개념      | 쉬운 설명·예시                                      |
| --------- | --------------------------------------------------- |
| Atoms     | 버튼·입력창·라벨 같은 작은 요소                     |
| Molecules | 라벨·입력창·버튼을 조합한 검색 입력 영역            |
| Organisms | 검색 입력 영역과 메뉴 등을 묶은 헤더 같은 화면 영역 |
| Templates | 화면 영역을 어디에 배치할지 정한 기본 틀            |
| Pages     | 기본 틀에 실제 내용을 넣은 화면                     |

단순히 작은 것부터 순서대로 모두 만들어야 하는 개발 절차는 아닙니다. 요구사항과 실제 화면을 함께 보면서 재사용할 부분을 검토합니다. 개념의 원래 설명은 [Brad Frost의 Atomic Design](https://atomicdesign.bradfrost.com/chapter-2/)에서 확인할 수 있습니다.

### 언제 적용하나요?

- 여러 화면에서 같은 역할·디자인의 버튼이나 폼을 반복해서 쓸 때
- 한 곳의 변경을 관련 화면에 일관되게 반영하고 싶을 때
- 화면 파일에 서로 다른 책임이 섞여 수정하기 어려워졌을 때

한 번 사용하는 간단한 화면은 그대로 두어도 됩니다. 처음부터 다섯 종류의 폴더를 만들거나, 모양만 비슷한 요소를 무조건 합칠 필요는 없습니다. 이 보일러플레이트는 해당 폴더나 공통 UI 세트를 미리 생성하지 않았으며, 현재 시작 안내 화면도 그대로 유지합니다.

Next.js 화면은 계속 src/app/에 만듭니다. Pages는 디자인상의 개념이며 별도의 src/pages/ 폴더를 만들라는 의미가 아닙니다. 데이터 저장·권한 처리 같은 서버 책임도 화면의 작은 표시 요소와 구분해야 합니다.

### Codex에 요청하는 예시

> 화면에서 반복되는 버튼·입력창·폼을 확인하고 공통 컴포넌트로 분리할 이점이 있는지 검토해 주세요. 아토믹 디자인은 참고하되 모든 계층·폴더를 강제로 만들지 마세요. 필요한 변경과 영향을 먼저 보여 주세요. 아직 파일은 이동하거나 분리하지 마세요.

수정안을 확인할 때는 어떤 화면이 함께 바뀌는지, 이해하기 쉬워지는지, 모바일·키보드 사용과 오류 상태가 유지되는지 확인하세요. 에이전트의 상세 판단 기준은 [프론트엔드 지침](../.agent/frontend.md#아토믹-디자인의-선택적-적용)에 있습니다.

## 오류를 전달할 때

명령어를 더 실행하거나 파일을 삭제하기 전에, Codex에게 현재 상태 확인을 요청하세요.

> 실행이 되지 않습니다. 현재 폴더와 Node.js 버전, 설치 상태를 확인하고 원인을 설명해 주세요. 수정이나 설치가 필요하면 먼저 변경 내용을 보여주세요.

함께 알려주면 좋은 내용은 다음과 같습니다.

- 무엇을 하려고 했는지
- 실행한 명령과 오류가 발생한 시점
- 비밀값과 개인정보를 가린 오류 메시지
- Windows인지 Linux인지

실제 .env 내용이나 DB 연결 URL 전체를 붙여 넣지 마세요. Codex가 분석 결과와 수정안을 제시하면 확인한 뒤 필요한 변경만 승인합니다.

## 팀원과 함께 작업할 때

Git 명령을 외우지 않아도 다음처럼 요청할 수 있습니다.

### 기능을 나누어 개발하기 전

예약 기능과 회원 기능을 나누어도 같은 User 모델이나 공통 파일을 수정할 수 있습니다. 브랜치가 다르거나 Git 충돌 없이 합쳐진다는 이유만으로 중복·불일치가 없는 것은 아닙니다.

Codex는 기능 개발 전에 확인 가능한 관련 계획과 기존 구현을 비교합니다. 겹치는 대상이 있으면 대상·영향·조정안을 설명하며, 사용자는 공통 DB·파일을 누가 어떤 순서로 반영할지 확인하면 됩니다. 관련 plans/에는 기능 담당자, 수정 대상, 공유 영역, 먼저 완료되어야 하는 작업과 합의 결과를 기록할 수 있습니다. 계획 파일을 생략해도 이 검토는 필요합니다.

> [담당 기능]을 개발하기 전에 다른 사람의 작업과 겹치는 DB 모델·파일·공통 컴포넌트가 있는지 확인해 주세요. 기존 구현과 공유된 계획을 비교하고, 겹치면 영향과 담당·반영 순서 조정안을 먼저 알려 주세요. 확인하지 못한 작업도 구분해 주세요.

매번 전체 작업을 멈추는 절차는 아닙니다. 조정이 필요한 부분만 확인하고 독립적인 승인 작업은 계속 진행하며, 이미 합의한 같은 범위는 반복해서 묻지 않습니다. 에이전트가 다른 사람의 브랜치나 미공유 작업을 자동으로 아는 것은 아니므로 팀원끼리 계획과 진행 상황을 공유하세요. 확인할 수 없는 부분은 검토 한계로 남깁니다.

담당·공유 영역 기록은 [계획 양식](../plans/README.md), 검토 절차는 [협업 지침](../.agent/collaboration.md#기능별-업무분장과-중복-검토)을 참고하세요.

### 팀 변경 확인과 반영 요청

> 팀 작업을 시작하려고 합니다. 현재 브랜치와 미완료 변경, 팀 변경 확인에 필요한 절차를 설명해 주세요. 변경 작업은 승인받은 뒤 진행해 주세요.

> 이번 작업을 팀 작업과 합쳐도 되는지 검사하고, 겹치는 변경과 확인이 필요한 부분을 쉬운 말로 설명해 주세요.

팀 변경 반영·충돌 처리·검사는 [협업 지침](../.agent/collaboration.md)에 따라 안내합니다. 검사 완료가 commit·push·merge까지 자동 승인한 것은 아닙니다.

## 요청과 승인

이 프로젝트는 관련 파일 확인 → 계획과 변경 내용 제시 → 사용자 승인 → 적용 → 검증 순서로 작업하도록 구성되어 있습니다.

- 분석·검토·가능 여부 질문은 파일 변경 승인이 아닙니다.
- 제안 내용을 확인한 뒤 “위 변경 내용을 적용하라”처럼 명확하게 승인합니다.
- 파일 생성·수정·삭제, 패키지 설치, DB 변경과 배포는 공통 승인 규칙을 따릅니다.
- DB 모델 파일 수정, 마이그레이션 생성, 실제 DB 적용은 서로 다른 작업입니다. 필요한 범위를 구분해서 승인하세요.
- 결과를 확인할 때 변경 파일, 검사 결과와 실제로 실행하지 못한 항목을 함께 확인하세요.

예를 들어 모델 수정만 승인했다면 실제 DB 테이블까지 변경된 것으로 생각하면 안 됩니다.

변경안을 확인할 때 일부 예시인지, 실제 적용할 전체 변경인지 구분하세요. 정해진 범위에서 사전 코드 제시를 생략하도록 요청할 수 있지만, 실제 DB 변경·배포·Git 작업까지 함께 승인되는 것은 아닙니다.

검증 결과는 자동 검사·실제 DB·HTTP·브라우저 동작·화면 배치를 구분해서 확인하세요. 문서 갱신을 보류했다면 현재 코드와 다른 설명이 남을 수 있으므로 그 차이도 함께 확인하세요.

## 지침 개선 제안

프로젝트 구조·명령·인증·테스트·배포 방식이 바뀌거나 같은 문제가 반복되면 Codex가 지침 개선 필요성을 검토하도록 구성되어 있습니다.

Codex가 변경 이유, 대상 문서, 수정 문구와 영향을 제시하면 내용을 확인하고 적용 여부를 결정하세요. 기존 작업 승인만으로 별도의 지침 변경까지 자동 승인되는 것은 아닙니다. 제안한 내용이 필요하지 않으면 적용하지 말라고 알려주세요.

설정·명령·사용 절차·공통 정책이 바뀌면 사용자 문서인 docs/와 에이전트 지침인 .agent/ 사이에 다른 안내가 생기지 않았는지도 함께 검토합니다. 두 문서를 똑같이 복제하는 것이 아니라, 사용자가 알아야 할 영향과 에이전트가 지킬 구현·검증 기준이 일치하는지 확인합니다. 차이가 있으면 원인과 수정안을 확인한 뒤 승인된 범위에서 반영합니다.

설치·DB·배포 안내는 담당 docs/ 문서에서 갱신하고, README의 프로젝트 작성 양식은 유지합니다. 새 프로젝트의 작성자 정보를 바꿔도 보일러플레이트의 기존 MIT 저작권·허가 고지는 보존합니다. [제작자 정보와 라이선스 안내](CUSTOMIZE_PROJECT.md#3-제작자-정보와-라이선스)도 참고하세요.

지침을 변경했다면 다음 요청에서 적용할 문서와 규칙을 다시 확인하도록 요청할 수 있습니다.
