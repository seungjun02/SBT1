# 비개발자를 위한 보안 안내

보안은 비밀번호뿐 아니라 누가 어떤 정보에 접근하고 어떤 비용을 발생시킬 수 있는지 관리하는 일입니다. 처음 기능을 계획하고 외부에 공개하기 전에 관련 항목을 확인하세요. 모든 항목을 외울 필요는 없으며 에이전트에 필요한 검토를 요청하면 됩니다.

이 문서는 작업 기준입니다. 문서가 있거나 타입·린트·빌드 검사가 통과했다고 실제 보안 검증이 완료된 것은 아닙니다. 복사한 프로젝트는 현재 코드·설정과 실제 접근 결과를 확인해야 합니다. 인증·로그인·권한 기능이 초기 보일러플레이트에 구현되어 있다고 가정하지 마세요.

## 먼저 지킬 원칙

| 확인할 것         | 쉬운 기준                                                                   |
| ----------------- | --------------------------------------------------------------------------- |
| 비밀값            | DB 비밀번호·접속 URL·인증 비밀키·토큰은 GitHub·화면·채팅·로그에 올리지 않기 |
| 관리자·회원 권한  | 메뉴를 숨기는 것과 별개로 서버에서 역할과 자료 소유자 확인                  |
| 입력과 출력       | 브라우저 검사를 우회해도 서버가 검사하고, 외부 글·파일을 안전하게 표시      |
| DB·파일 공개 범위 | 테이블·Storage·다운로드 URL에 누가 접근하는지 확인                          |
| 오용과 비용       | 로그인·메일·업로드·유료 API에 요청 제한과 사용량 관리 검토                  |
| 유지보수          | 공식 보안 공지와 지원 버전 확인, 업데이트 영향 검증                         |

## 비밀값과 공개용 값 구분

실제 비밀값은 로컬 환경 파일이나 배포 서비스의 서버 환경 변수로 관리하고 `.env.example`에는 예시만 둡니다. `NEXT_PUBLIC_`는 브라우저에 공개될 수 있는 값에 사용하는 이름입니다. 비밀값에 붙이면 안 됩니다. `.gitignore`에 적어도 이미 Git에 등록된 파일이나 과거 이력까지 자동으로 지워지지는 않습니다.

Supabase의 publishable 키와 기존 anon 키는 공개용으로 사용할 수 있지만 데이터 접근 정책이 필요합니다. secret 키·기존 service_role 키·DB 비밀번호는 공개하지 않습니다. 이들 관리자 키는 RLS를 우회할 수 있으므로 키의 이름·용도와 권한을 구분해야 합니다. 공개 CA 인증서는 DB 비밀번호와 다르며, 공식 출처·내용을 확인해 포함할 수 있습니다. [Supabase 데이터 보호](https://supabase.com/docs/guides/database/secure-data)

에이전트에는 환경 파일 전체 대신 필요한 변수의 존재 여부만 확인하도록 요청하세요. 오류 메시지·스크린샷·URL 검색 매개변수에도 비밀값이 들어갈 수 있습니다. 안전한 전달 방법은 [오류 안내](TROUBLESHOOTING.md)를 참고하세요.

## 로그인과 권한은 별개입니다

로그인은 누구인지 확인하는 것이고 권한은 그 사람이 해당 자료를 조회·수정할 수 있는지 판단하는 것입니다. 관리자 주소를 숨기거나 버튼을 비활성화해도 직접 요청할 수 있으므로 Server Action·REST API의 실제 처리에서 검사해야 합니다. [Next.js 인증·권한 안내](https://nextjs.org/docs/app/guides/authentication)

비회원·일반 회원·관리자의 접근 범위를 정하고 다른 회원의 자료에도 접근할 수 없는지 확인합니다. 가입 요청에 관리자 역할을 넣거나 자료 ID를 바꿔 보냈다고 권한이 생겨서는 안 됩니다. 비밀번호 해싱·세션·로그아웃·계정 복구는 검증된 인증 도구를 활용하세요. MVP에서 메일 인증을 생략할 때의 제한은 [인증 안내](AUTHENTICATION.md)를 따릅니다.

## 입력·DB·파일·외부 서비스

- 화면 검사는 빠른 안내용이며 서버에서도 다시 검사합니다. 필요한 필드만 받아 저장하고 서버의 업무·권한 규칙을 확인합니다. [유효성 검사 안내](VALIDATION.md)
- 올바른 입력 형식만 검사한다고 악성 HTML이나 위험한 DB 쿼리까지 막히지는 않습니다. 외부 글을 HTML로 표시하거나 검색 조건을 쿼리에 넣는 기능은 출력·쿼리 방식도 검토합니다. [OWASP 입력 검증](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)
- Prisma로 접속할 때 로그인한 사용자의 Supabase 세션이 자동 전달되지는 않습니다. 서버 권한 검사와 DB 연결 역할을 확인하세요. 브라우저 Data API를 사용한다면 테이블의 RLS 정책·권한도 확인합니다. DB만 사용한다면 불필요한 API 노출 축소를 검토할 수 있습니다. [DB 안내](SUPABASE_SETUP.md)
- 파일 업로드에는 크기·형식·실제 내용·저장 위치·다운로드 권한 확인이 필요합니다. 공개 버킷에 저장하면 의도하지 않은 사람이 파일을 볼 수 있으므로 실제 공개 설정을 확인합니다.
- 사용자가 입력한 주소를 서버에서 가져오거나 외부 웹훅을 받는 기능은 허용 주소·서명·중복 요청 처리를 검토합니다. 연동이 된다는 이유만으로 모든 외부 입력을 신뢰하지 않습니다.
- 로그인·메일·파일·유료 API의 과도한 사용을 막을 방법을 정하세요. 요금 경보가 비용을 자동 차단하는지는 서비스별로 확인해야 합니다. 무료 플랜이나 숨겨진 버튼만으로 오용 방지가 끝나지는 않습니다.

## 외부 공개·배포 전 확인

관련 기능에서 비밀값 노출, 익명·다른 회원·관리자의 접근, 공개 테이블·파일, 메일·유료 API 사용 제한을 확인합니다. 로컬·Preview·Production의 환경 변수와 권한이 같은지 추측하지 말고 각각 확인하세요. 실제 데이터 변경·메일·비용을 발생시키는 테스트는 승인한 환경·범위에서 진행합니다.

의존성과 Node.js의 공식 보안 공지를 확인하고 업데이트 영향에 맞게 검사합니다. `npm audit` 결과만으로 보안을 보장할 수 없고, 자동 강제 수정 명령을 바로 실행하면 호환성이 깨질 수 있습니다. 설치·업데이트·인증·권한·배포 설정 변경은 변경안과 승인 범위를 먼저 확인하세요. [배포 안내](VERCEL_DEPLOYMENT.md)

## 키나 비밀번호가 노출되었다면

1. 노출된 값을 다시 채팅·문서·로그에 붙이지 말고 키 종류와 노출 위치·범위를 알립니다.
2. 제공 서비스에서 해당 키·비밀번호를 폐기·교체하는 방안과 서비스 영향을 확인합니다. 단순히 파일을 지우는 것만으로 유출이 해소되지는 않습니다.
3. 사용 중인 로컬·배포 설정을 교체하고 필요한 재배포·세션 폐기·접근 로그 확인을 계획합니다. 실제 운영 변경은 승인된 범위에서 진행합니다.
4. 저장소·배포 자산 등 남은 노출 경로를 정리합니다. Git 이력 재작성은 협업에 영향을 주므로 별도 합의 후 수행합니다. 이력 정리만으로 이미 노출된 키가 다시 안전해지지는 않습니다.

키 회전은 기존 연결을 끊을 수 있습니다. 에이전트는 노출을 발견하면 영향과 대응안을 먼저 설명하고 자동으로 계정·운영 설정을 바꾸지 않도록 구성합니다. [OWASP 비밀값 관리](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

## 에이전트에 요청하기

```text
[기능 또는 공개할 범위]를 docs/SECURITY.md 기준으로 검토해 주세요.
현재 코드·설정을 확인해 비밀값 노출, 서버 권한, 입력·출력,
DB·파일 공개 범위와 오용·비용 위험 중 관련된 항목을 살펴 주세요.
확인된 문제·영향·수정안·검증 방법과 접근하지 못한 설정을 구분해 주세요.
비밀값은 출력하지 말고 아직 파일·패키지·권한·DB·배포 설정은 변경하지 마세요.
```

계획을 사용하는 작업은 관련 위험·대응·검증 근거를 [계획 양식](../plans/README.md)에 남깁니다. 보안 검토 결과에는 코드 검토·정적 검사·실제 접근 테스트·배포 확인과 미검증 범위를 구분합니다. 에이전트의 상세 기준은 [보안 지침](../.agent/security.md), 작업 절차는 [Codex 안내](CODEX_GUIDE.md)를 참고하세요.
