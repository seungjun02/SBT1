# 서버 지침

Server Action·Route Handler·서버 함수·인증·권한·입력 검증·캐시·환경 변수 작업에 적용한다.
공통 승인 규칙은 [AGENTS.md](../AGENTS.md), 개발 순서·계획·관심사 분리·공통 검증은 [개발 지침](development.md)을 함께 따른다.

DB 접근은 [DB 지침](database.md), 배포 영향은 [배포 지침](deployment.md), 오류 분석은 [오류 추적 지침](troubleshooting.md)도 읽는다. 화면과 연결할 때는 [프론트엔드 지침](frontend.md)을 함께 적용한다.

## 인증 방식 확인

- 회원가입·로그인 요청을 받으면 [인증 방식 선택 안내](../docs/AUTHENTICATION.md)를 안내하고, 인증 방식이 정해졌는지 확인한다. 미정이면 요구사항에 맞는 선택지를 쉬운 말로 비교·제안한다. 이미 결정된 방식은 반복해서 묻지 않으며, 안내만으로 패키지를 설치하거나 인증·DB 설정을 변경하지 않는다.

## Cache Components와 데이터 처리

- 기능 개발 시 실제 Next.js 버전과 현재 설정·호출 경로를 먼저 확인한다. DB 조회·cookies·세션 등 요청별 처리를 어디서 수행할지 정하고, 필요한 Suspense·로딩 UI·캐시 범위·갱신 방침을 구현안에 포함한다. 설정 선택을 비개발자의 선행 과제로 넘기지 않는다.
- 기존 구조로 처리할 수 있으면 유지한다. 예제와 다르다는 이유만으로 캐시·렌더링 설정·DB 드라이버·Tailwind 로더를 교체하지 않는다. 관련 설정 변경이 꼭 필요하면 호환성 근거·기능 및 배포 영향·검증 방법을 설명하고 승인 범위에서 적용한다.

- 현재 next.config.ts의 cacheComponents·partialPrefetching을 기준으로 개발하며, 오류 회피를 위해 임의로 끄지 않는다.
- 요청마다 새 데이터가 필요한 DB 조회·cookies·headers 등의 동적 영역은 적절한 Suspense 경계와 로딩 표시를 갖도록 구성한다.
- 캐시는 재사용 범위와 갱신 시점이 정해진 데이터에 명시적으로 적용한다. 모든 Prisma 조회가 자동 캐시된다고 가정하지 않는다.
- 사용자별 데이터와 권한에 따라 달라지는 응답을 공용 캐시에 임의로 저장하지 않는다.
- 데이터 변경 후에는 선택한 정책에 맞게 revalidatePath·revalidateTag·updateTag 등의 필요성과 사용 위치를 검토한다. 함수의 실제 지원 범위·버전은 확인하고 적용한다.
- DB 화면 변경은 개발 모드뿐 아니라 빌드에서도 확인한다. 상세 설명은 [설치 안내](../docs/SETUP.md#cache-components를-사용하는-기능-개발)를 참고한다.

## 서버 입력·권한·오류 결과

- 검증 스키마를 공유하더라도 서버에서 입력을 다시 검증한다.
- 사용자 입력 검증과 로그인·권한 검사는 별개로 수행한다.
- Server Action과 Route Handler에서도 사용자와 대상 데이터의 접근 권한을 검사한다.
- 예상 가능한 검증 실패와 예기치 않은 예외를 구분한다. 빈 catch나 무조건 성공 응답으로 오류를 숨기지 않는다.
- 서버 로그에는 비밀값·입력 본문을 남기지 않으면서 작업 이름과 안전한 오류 코드 등 추적 정보를 제공한다.
- 개인정보 응답을 사용자 간 공유 캐시에 저장하지 않도록 캐시 범위를 확인한다.

## 화면·서버 유효성 검사

- 입력받는 기능의 계획·구현 시 [유효성 검사 안내](../docs/VALIDATION.md)를 참고해 필수값·형식·범위·허용 필드·정규화 규칙과 실패 메시지를 먼저 정한다. 입력과 무관한 단순 화면 작업에 검증 코드나 계층을 추가하지 않는다.
- 화면은 React Hook Form·Zod·resolvers로 빠르게 안내하고, 모든 서버 진입점은 신뢰할 수 없는 입력으로 취급해 다시 검사한다. Server Action과 Route Handler의 body·FormData·경로·검색 매개변수를 실제 타입으로 파싱하고 검증 성공 후의 값만 처리한다. TypeScript 타입이나 클라이언트 검사 성공을 런타임 검증으로 간주하지 않는다.
- 공통 형식 규칙은 기존 구조에 맞는 작은 Zod 스키마로 공유할지 검토한다. 브라우저에 공유하는 모듈에는 DB·비밀값·서버 전용 import를 넣지 않는다. 서버 전용 업무·권한 검사까지 공유 스키마에 억지로 합치지 않는다.
- 허용 필드를 명시해 DB 쓰기를 구성하고 요청 본문 전체를 그대로 전달하지 않는다. 사용자 ID·소유자·역할·가격 등 신뢰해야 하는 값은 세션·서버 데이터로 결정하거나 변경 권한을 검증한다. 공백·빈값·숫자·날짜 변환 규칙은 의도하지 않은 값이 통과하지 않도록 명시하며 비밀번호는 임의로 trim·변환하지 않는다.
- 서버에서 로그인·소유권·업무 규칙을 별도로 확인한다. 중복·재고·예약 가능 여부의 사전 조회만으로 동시 요청 안전성을 보장하지 말고 DB 지침과 함께 고유·관계 제약·원자적 갱신·트랜잭션 필요성을 검토한다. 실제 스키마·DB 변경은 승인 범위를 따른다.
- 예상 가능한 실패는 안전한 필드별·폼 전체 오류로 화면에 연결한다. 기존 API 응답 계약을 유지하고 오류 객체·입력 본문을 그대로 노출하지 않는다. 예기치 않은 오류는 [오류 추적 지침](troubleshooting.md)을 따른다.
- 정상 입력뿐 아니라 빈값·잘못된 타입·최소/최대 경계·허용하지 않은 필드·브라우저 검사 우회·권한 없는 요청을 검증한다. 관련 기능에는 중복·동시 요청도 확인하고 실제 데이터 변경 테스트는 승인된 환경·범위에서 수행한다. 계획 사용 시 입력 규칙·검사 위치·결과·미검증 범위를 기록한다.

## 환경 변수와 호환성

- DB 변수는 `src/lib/env.ts`에서 서버 전용으로 검증하고 비밀값에 `NEXT_PUBLIC_`를 붙이지 않는다.
- 환경 파일, 로딩 우선순위, 공개 여부를 바꾸면 앱과 Prisma CLI에 미치는 영향을 함께 확인한다.
- Linux의 파일명·변수명 대소문자를 고려하고 운영체제 전용 절대 경로를 앱 코드에 넣지 않는다.
- 환경 파일이나 설치 절차가 바뀌면 승인된 범위에서 docs/SETUP.md·docs/SUPABASE_SETUP.md·docs/VERCEL_DEPLOYMENT.md 중 해당 절차를 담당하는 문서를 갱신한다. README는 시작 안내 링크의 유효성을 확인하고 작성 양식을 임의로 변경하지 않는다.
