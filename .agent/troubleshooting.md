# 오류 추적 지침

페이지·Server Action·REST API·DB 연결·빌드·배포 오류의 원인 분석과 수정 확인에 적용한다.
공통 승인 규칙은 [AGENTS.md](../AGENTS.md), 개발 순서·계획·관심사 분리·공통 검증은 [개발 지침](development.md)을 함께 따른다.

관련 화면은 [프론트엔드 지침](frontend.md), 서버 처리는 [서버 지침](server.md), DB는 [DB 지침](database.md), 빌드·배포·운영 장애는 [배포 지침](deployment.md)을 필요한 범위에서 함께 읽는다.

## 페이지·서버 오류 추적

- [오류 확인과 전달 안내](../docs/TROUBLESHOOTING.md)를 참고하고, 재현 조건·페이지 경로·발생 시각과 시간대·실행 환경을 확인한 뒤 분석 순서와 원인 후보를 설명한다. 페이지의 호출 코드에서 Server Action·Route Handler·외부 API·Server Component 직접 조회 중 실제 사용 방식을 확인한다.
- 화면 → 호출 코드 → 서버 처리 → DB·외부 서비스 순으로 관련 경로를 추적한다. 브라우저에서 요청하기 전에 실패했는지, 서버가 호출되었는지, 결과를 화면에 연결하는 과정에서 실패했는지 구분한다. Server Component의 직접 조회가 브라우저 Network에 별도 API 요청으로 보인다고 가정하지 않는다.
- 로컬 서버 오류는 해당 개발 서버 터미널, 브라우저 오류는 Console·Network, 배포 후 서버 오류는 해당 Vercel 배포의 Runtime Logs, 빌드 오류는 빌드 로그를 확인한다. Server Action 요청도 Network에서 확인할 수 있지만 HTTP 상태만으로 업무 성공·실패를 판단하지 않고 반환 결과와 서버 로그를 대조한다.
- 예상 가능한 입력·업무 실패는 안전한 구조화된 결과와 화면 안내를 확인한다. 예기치 않은 오류는 작업 이름·안전한 오류 코드 등 원인 추적 정보를 서버에 남기는지 검토한다. 운영 응답에서 상세 오류가 생략될 수 있으므로 화면의 digest·발생 시각·요청 식별자가 있으면 로그와 대조하되 항상 제공된다고 가정하지 않는다.
- 에이전트가 다른 터미널·브라우저·배포 로그에 자동 접근할 수 있다고 가정하지 않는다. 접근하지 못하면 그 한계를 밝히고 관련 오류 구간·상태 코드 등 최소 정보만 요청하며, 확보한 코드로 가능한 분석은 계속한다. 로그가 없다는 이유만으로 정상이라고 판단하지 않는다.
- 비밀번호·토큰·쿠키·Authorization 헤더·DB URL·실제 개인정보를 로그·응답·답변에 노출하지 않는다. 오류 객체·요청 본문 전체 출력, HAR·전체 Network 기록·.env 공유를 기본 해결책으로 제안하지 않는다.
- 분석을 이유로 데이터 변경 요청을 재전송하거나 인증·캐시·TLS 검증을 해제하지 않는다. 수정·로그 추가·재현 시 실제 DB 쓰기·배포는 승인 범위를 확인한다. 수정 후 재현 조건과 실패 경로를 다시 확인하고 실제 검증·미검증 항목을 구분한다.
