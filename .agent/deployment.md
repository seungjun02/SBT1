# 배포 지침

Vercel 설정, 빌드, 배포, 운영 환경 변수와 운영 장애 작업에 적용한다.
공통 승인 규칙과 작업 흐름은 [AGENTS.md](../AGENTS.md)를 따른다.

## 시작 전 확인

- 배포 전 보안 검토와 유출 대응은 [보안 지침](security.md)을 함께 적용한다. 실제로 확인한 설정·검증과 미확인 항목을 구분하며 보안 설정을 자동 변경하지 않는다.

- 대상 프로젝트, 환경, 변경 목적과 영향 범위를 확인한다.
- `package.json`, `next.config.ts`, `.nvmrc`, README와 실제 배포 설정을 확인한다.
- Node.js 버전은 `package.json`의 engines와 일치시키고 해당 계열의 보안 패치를 확인한다.
- 빌드 오류는 먼저 로그와 재현 조건을 확인한다. 타입·린트 검사를 끄는 방식으로 해결하지 않는다.
- 앱 코드와 DB 변경이 있으면 [개발 지침](development.md)과 [DB 지침](database.md)도 읽는다.

## Vercel 설정과 비밀값

- Framework Preset은 Next.js, 설치 명령은 `npm ci`, 빌드 명령은 `npm run check && npm run build`를 기준으로 한다.
- Root Directory는 실제 저장소 구조에 맞춘다. 폴더명을 복사한 프로젝트에서 고정값으로 가정하지 않는다.
- Development·Preview·Production 환경 변수를 분리한다.
- Vercel 배포 환경과 연결 DB의 용도(개발·테스트·운영)를 각각 확인한다. Production 배포라는 이유만으로 운영 DB라고 가정하지 않는다.
- GitHub 연결은 필요한 저장소만 선택하고, 부여할 접근 권한과 승인 범위를 확인한다.
- Preview를 운영 DB에 연결하지 않는다. 별도 Supabase 프로젝트나 적합한 DB 브랜치를 사용한다.
- DB 기능이 있으면 앱 실행 환경에 `DATABASE_URL`을 제공한다.
- 환경 변수는 앱에서 실제 사용하는 항목만 등록한다. Supabase Auth를 사용하는 경우 해당 구현이 요구하는 공개 URL·공개 키를 확인하며, 관리자 키를 일반 앱 배포에 포함하지 않는다.
- `DIRECT_URL`은 별도 마이그레이션 작업에만 제공하는 구성을 우선 검토한다.
- 비밀값을 코드·로그·클라이언트 공개 환경 변수에 넣지 않는다.
- 비밀값 입력 영역을 포함하는 전체 UI 상태·스크린샷을 출력하지 않는다. 마스킹된 입력란도 도구 결과에 원문이 포함될 수 있으므로 변수 이름·등록 여부·적용 환경만 확인한다.
- 비밀값이 출력되면 값을 재출력하지 않고 사용자에게 알린다. 관련 자격 증명 교체·연결 설정 갱신·재배포는 승인된 범위에서 수행한다.
- 공개 `NEXT_PUBLIC_` 값은 빌드 시 반영되는 특성이 있으므로 변경 후 재빌드·재배포 필요성을 확인한다.
- Vercel 함수와 Supabase DB의 리전, 연결 풀 한도와 실행 시간을 확인한다.
- GitHub Actions는 선택 사항이다. 기본 `.github/` 폴더를 전제로 하지 않으며, 필요하면 docs/GITHUB_ACTIONS.md의 예시를 설명하고 승인 후 추가한다.
- 요구가 없으면 `vercel.json`, Docker, 별도 운영 설정 파일을 추가하지 않는다.

## 배포 순서

1. 변경 파일과 위험, 검증 결과, 배포 대상, 필요한 설정을 먼저 설명한다.
2. 승인된 로컬 검사와 빌드로 오류를 확인한다. 빌드 성공을 배포 성공으로 보고하지 않는다.
3. DB 변경이 있으면 이력·백업·호환성·적용 순서를 별도로 검토하고 승인받는다.
4. 실제 배포와 환경 변수 변경은 해당 작업에 대한 승인이 확인된 경우에만 실행한다.
5. 배포 후 승인된 범위에서 첫 화면·핵심 경로·로그와 환경별 연결을 확인한다.

- 모든 Vercel 빌드에 운영 마이그레이션을 연결하지 않는다.
- 코드 배포 롤백이 DB 스키마나 데이터를 자동 복원한다고 가정하지 않는다.
- 장애 조사 중 로그의 비밀값·사용자 정보를 그대로 출력하지 않는다.
- 운영 명령, 계정·설정 변경과 복구 작업은 명시적 승인 범위를 지킨다.

## 검증과 전달

- `npm run check`, `npm run build`와 변경에 맞는 주요 기능을 확인한다.
- DB가 필요 없는 기본 첫 화면은 DB 연결 정보 없이 빌드되는 구성을 유지한다.
- `npm audit` 결과와 Node.js 런타임 보안 상태는 별개로 관리한다.
- Linux/Vercel에서 직접 확인하지 않았다면 Windows 검사만으로 해당 환경 검증이 완료됐다고 말하지 않는다.
- 성공·실패, 실제 반영 여부, 미검증 항목과 추가 작업을 구분해 보고한다.
- 배포 후 화면 접근·DB 읽기·DB 쓰기·인증과 권한 검증 결과를 구분한다. 앱에 없는 기능은 검증 대상으로 가정하지 않으며, 데이터 생성·수정·삭제는 승인 범위에서만 수행한다.
- 보일러플레이트 배포본 전달 시 공통 지침의 생성물 제외 규칙을 따른다.
