# 보안 지침

인증·권한·개인정보·비밀값·외부 입력·공개 API·파일 업로드·외부 서비스 연동, 배포 전 보안 검토와 유출 대응에 적용한다. 공통 승인 규칙은 [AGENTS.md](../AGENTS.md), 개발 흐름은 [개발 지침](development.md)을 따른다. 사용자에게는 [보안 안내](../docs/SECURITY.md)를 필요한 범위에서 제공한다.

## 적용 범위와 결과 보고

- 실제 코드·설정·의존성·호출 경로를 확인하고 보호할 정보, 호출 주체, 공개 범위와 관련 위험을 판단한다. 보일러플레이트의 초기 설명만으로 복사한 프로젝트가 안전하다고 판단하지 않는다.
- 관련 항목만 적용한다. 단순 문구·스타일 수정에 전체 점검을 강제하거나 독립적인 승인 작업을 중단하지 않는다. 이미 정한 같은 범위의 정책은 반복 확인하지 않고 새로운 위험·미정 사항만 설명한다.
- 문제를 발견하면 확인 근거·영향·수정안·검증 방법을 쉬운 말로 제시한다. 확인되지 않은 위험은 원인 후보와 구분하고, 요청 범위 밖 설정 변경·패키지 설치·기능 추가를 자동 적용하지 않는다.
- 보안 테스트는 승인된 대상·범위에서 수행한다. 다른 사용자 데이터 접근·실제 데이터 변경·부하·메일·유료 API 비용을 발생시킬 수 있는 검사는 별도 범위를 확인한다. 외부 서비스에 무단 침투·대량 요청을 하지 않는다.

## 비밀값과 최소 공개

- DB URL·비밀번호·인증 비밀키·토큰은 서버 환경에서 관리한다. 공개해도 되는 값과 비밀값을 구분하고 비밀값에 NEXT*PUBLIC*를 붙이거나 Client Component·props·정적 자산·로그·계획·답변에 노출하지 않는다.
- .gitignore가 이미 추적된 파일·Git 이력·배포 자산의 비밀값까지 제거한다고 가정하지 않는다. 확인 시 값 자체 대신 변수명·경로·존재 여부를 제시하고 외부 검사 서비스에 비밀값을 업로드하지 않는다.
- Supabase publishable/anon 키는 공개용이지만 안전한 접근 정책을 대신하지 않는다. secret/service_role 키와 DB 비밀번호는 공개하지 않으며, 서버 코드라는 이유만으로 항상 관리자 키를 선택하지 않는다.
- 서버 응답은 필요한 필드만 포함한다. 오류 객체·요청 본문·쿠키·Authorization 헤더·개인정보 전체를 기록하지 않는다. 사용자별 데이터·세션을 공용 캐시에 저장하지 않는다.

## 인증·권한·데이터 경계

- 인증과 세션은 검증된 도구를 우선 활용하고 비밀번호 해싱·쿠키·만료·로그아웃·복구 정책을 확인한다. MVP의 메일 인증 생략은 [인증 안내](../docs/AUTHENTICATION.md)의 제한과 사용자 선택을 따른다. 인증 생략을 서버 권한 검사 생략으로 확대하지 않는다.
- Server Action도 외부에서 호출 가능한 서버 진입점으로 취급한다. UI·페이지·Proxy의 제한만 믿지 말고 실제 처리에서 인증·역할·소유권을 검사한다. 요청의 사용자 ID·관리자 역할·가격을 그대로 신뢰하지 않는다.
- 세부 입력 검증·허용 필드·업무 규칙은 [서버 지침](server.md), DB 제약·최소 권한·RLS·데이터 보존은 [DB 지침](database.md)을 적용한다. Prisma 연결에 사용자 세션이나 RLS 정책이 자동 적용된다고 가정하지 않는다.
- Data API·Storage·버킷·테이블의 실제 공개 여부와 역할별 접근을 확인한다. 사용하지 않는 노출의 축소를 제안하되 서비스 영향과 승인을 확인하고, 문제 해결을 위해 RLS·인증·TLS 검증을 끄지 않는다.

## 입력·출력·외부 연동

- 입력 검증만으로 XSS·SQL 인젝션이 방지된다고 판단하지 않는다. 안전한 파라미터 쿼리를 사용하고 외부 입력의 HTML 삽입·위험한 URL은 표시 문맥에 맞는 방어를 검토한다. dangerouslySetInnerHTML을 사용할 때 신뢰할 수 없는 HTML의 정화 필요성을 확인한다.
- 파일 업로드는 크기·허용 형식·실제 파일 내용·저장 경로·다운로드 권한을 검토한다. 파일명·MIME만 신뢰하지 않고 비공개 파일이 공개 URL로 노출되지 않도록 확인한다.
- 사용자 제공 URL의 서버 fetch는 허용 대상·내부 주소 접근·리디렉션을 검토한다. 외부 응답·웹훅은 신뢰 경계로 보고 서명·재전송·중복 처리와 시간 제한을 필요에 맞게 검토한다.
- 쿠키 인증의 상태 변경 요청에는 도구가 제공하는 CSRF·Origin 방어를 유지하고 Route Handler·외부 클라이언트의 인증 방식을 확인한다. CORS는 인증·권한 검사를 대신하지 않는다. 리디렉션 목적지는 허용 범위를 검증한다.
- 로그인·가입·메일·업로드·유료 API에는 요청 제한·크기·시간 제한·사용량 경보·예산 통제 필요성을 검토한다. 여러 함수 인스턴스에서 메모리 카운터만으로 제한이 보장된다고 가정하지 않는다.

## 배포·유지보수·유출 대응

- [배포 지침](deployment.md)에 따라 환경별 비밀값·공개 URL·최소 권한·로그를 확인한다. 보안 헤더는 실제 기능·인증·외부 자산 영향을 검토해 제안하며 정책을 임의로 추가해 화면을 깨뜨리지 않는다.
- 의존성과 Node.js 보안 상태는 공식 공지·지원 버전으로 확인한다. npm audit는 단서이며 통과가 전체 보안 보장은 아니다. npm audit fix --force나 일괄 업데이트를 자동 실행하지 않는다. 설치·lock 변경은 승인 범위를 따른다.
- 유출 의심 시 비밀값을 다시 출력하지 않고 종류·노출 위치·영향을 알린다. 해당 키 폐기·재발급, 연결 설정 교체·재배포, 필요 시 세션 폐기와 접근 로그 확인을 제안한다. 키 회전·운영 변경·Git 이력 정리는 승인 범위에서 수행하며, 이력 삭제만으로 노출된 키가 안전해진다고 설명하지 않는다.
- 코드 검토·정적 검사·실제 접근 제어 테스트·배포 설정 확인을 구분해 보고한다. 실행하지 않은 검사와 남은 위험을 명시하고 보안 기능이 없는 초기 상태를 구현 완료로 기록하지 않는다. 계획을 쓰는 승인된 작업에서는 위험·대응·근거·미검증 항목을 기록한다.
