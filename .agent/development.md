# 개발 지침

화면·스타일·폼·API·기능 개발, 버그 수정과 리팩토링에 적용한다.
공통 승인 규칙과 작업 흐름은 [AGENTS.md](../AGENTS.md)를 따른다.

## 시작 전 확인

- `package.json`, 관련 페이지·컴포넌트·설정과 기존 스타일을 먼저 확인한다.
- 버그 분석은 재현 조건과 원인 후보, 확인 순서를 먼저 설명한다.
- DB 접근이 있으면 [DB 지침](database.md), 배포 영향이 있으면 [배포 지침](deployment.md)도 읽는다.
- 현재 구조로 해결할 수 있으면 새 폴더나 계층을 추가하지 않는다.

## 초기 설정의 기술적 복잡성 관리

- 기능을 추가하기 전에 package.json·lock 파일, next.config.ts, TypeScript·Tailwind·Prisma 설정과 실제 관련 코드를 확인한다. 보일러플레이트 설명이나 최신 예제만으로 현재 버전·동작을 가정하지 않는다.
- 기존 설정으로 요구사항을 충족하면 유지한다. 별도 API·패키지·계층을 일률적으로 추가하거나 오류 회피를 위해 기능 설정을 끄지 않는다. 변경이 필요하면 현재 문제·권장안·이유·대상 파일·영향·검증 방법을 먼저 제시한다.
- 비개발자에게 캐시·로더·드라이버 등 내부 기술 선택을 시작 조건으로 요구하지 않는다. 서비스 동작·비용·배포·데이터 보호에 영향을 주는 선택을 쉬운 말로 설명하고, 합리적인 권장안을 제시하되 확인된 요구와 승인 범위를 지킨다.
- DB 조회·인증·쿠키·캐시를 다루면 [서버 지침](server.md#cache-components와-데이터-처리)을 적용한다. 설정·명령을 실제 변경하면 해당 사용자 안내와 지침의 일치 여부를 검토한다. 단순 문서 개선을 실제 기술 설정 변경으로 보고하지 않는다.

## 상세 지침 선택

- 화면·스타일·폰트·공통 UI·폼 사용성: [프론트엔드 지침](frontend.md).
- Server Action·Route Handler·인증·권한·검증·캐시·환경 변수: [서버 지침](server.md).
- 버그 원인 분석·로그 추적·수정 후 재현 확인: [오류 추적 지침](troubleshooting.md).
- 기능 개발·코드 검토 시 인증·권한·입력·개인정보·공개 범위 등 관련 위험을 먼저 판단하고, 해당하면 [보안 지침](security.md)을 함께 읽는다. 단순 문구·스타일 수정에 전체 보안 점검을 강제하지 않는다.
- 화면과 서버를 연결하는 기능은 프론트엔드·서버 지침을 함께 읽는다. 브라우저의 입력 안내만 바꿀 때도 서버 검증과 일치하는지 확인하고 관련 서버 기준을 참고한다. 로그인 기능은 서버·DB 지침과 필요한 화면 지침을 읽는다.
- 문서 링크만으로 해당 파일이 자동 로딩된다고 가정하지 않는다. 관련 파일을 실제로 읽고 적용하며, 공통 기준을 각 상세 지침에 중복 복사하지 않는다.

## 새 기능의 기본 진행 순서

데이터 저장이 필요한 새 기능은 다음 순서를 기본으로 한다. 사용자가 결과를 이해할 수 있도록 현재 단계와 판단·검증 결과를 쉬운 한국어로 설명한다.

1. **요구사항 분석·계획:** 사용자·문제·사용 흐름·입출력·완료 기준을 확인한다. 화면 설계와 서버·DB 필요성도 이때 함께 검토하고 변경 대상·영향·검증 방법을 제시한다.
2. **DB 분석·필요 시 수정:** 기존 모델·관계·제약·권한·날짜 처리와 데이터 영향을 확인한다. 기존 구조로 충분하면 모델 변경은 생략한다. 스키마 수정, Client 생성, 실제 마이그레이션을 구분하고 각각 승인 범위를 확인한다. 관련 DB 지침을 함께 적용한다.
3. **서버 처리:** 기능에 맞게 Server Action·Route Handler·서버 함수를 선택한다. 별도 API나 계층을 일률적으로 추가하지 않는다. 입력 검증·필요한 인증과 권한·DB 처리·오류 결과를 구현한다.
4. **화면 구현:** 계획에서 정한 흐름과 서버 처리에 맞춰 화면·폼을 연결한다. 로딩·성공·오류·빈 상태, 접근성·모바일 사용과 중복 제출을 확인한다. Cache Components 처리 기준도 적용한다.
5. **연결·권한·동작 검증:** 정상·실패·권한 없는 경우를 검증하고 타입·린트·서식·빌드를 확인한다. 실제 DB 쓰기·마이그레이션·배포는 승인된 대상과 범위에서만 수행한다. 로컬·DB·배포 환경에서 확인한 결과와 미검증 항목을 구분한다.

- 단계는 기능에 맞게 생략·반복할 수 있다. 화면만 바꾸는 작업에 DB 변경이나 서버 계층을 만들지 않는다.
- 검토 결과 구현 중 요구사항이나 데이터 구조가 달라지면 관련 계획과 영향 범위를 다시 확인한다.
- 이미 승인된 범위 안에서 단계가 바뀌는 것만으로 같은 승인을 반복 요청하지 않는다. 새 범위·실제 DB 변경 등 추가 승인이 필요한 경우에 확인한다.
- 첫 화면은 이 순서를 설명하는 참고용 안내이며 자동 실행·진행 상태 추적 기능이 아니다. 사용자 안내는 [Codex 사용법](../docs/CODEX_GUIDE.md#새-기능을-만드는-기본-순서)과 일치하도록 유지한다.

## 계획 파일로 작업 이어가기

- 작업 초기에 관련 plans/ 파일과 기록 필요성을 확인한다. 여러 단계·여러 파일의 새 기능, DB 모델·권한·외부 API 등 영향이 큰 변경, 협업·인수인계·추후 재개가 예상되는 작업은 이유·기록 범위를 설명하고 작성 여부를 사용자에게 확인한다.
- 관련 계획이 있으면 새 파일 작성보다 재사용을 우선한다. 단순 문구·스타일 수정은 기본적으로 생략하되 사용자가 원하면 작성한다.
- 같은 작업 범위에서 이미 작성·생략을 결정했다면 확인을 반복하지 않는다. 사용자가 이미 명시적으로 계획 파일 작성을 요청·승인했다면 다시 같은 승인을 요구하지 않는다. 범위나 위험이 실질적으로 달라져 재검토가 필요하면 새 이유를 설명한다.
- 기록 여부를 확인하면서 독립적인 읽기 전용 분석과 이미 승인된 작업을 불필요하게 중단하지 않는다. 파일 작성을 생략해도 필요한 채팅 계획·승인·검증 절차는 따른다.
- 생성 전 [계획 작성 안내](../plans/README.md)를 읽고 채팅에 전체 초안과 생성 경로를 제시한다. 사용자가 승인한 경우에만 파일을 생성한다. 실제 기능이 정해지지 않은 보일러플레이트에는 예시 기능의 실제 계획을 미리 만들지 않는다.
- 파일명은 YYYYMMDD-HHmmss-작성자-작업명.md로 정하고 생성 시 실제 KST(Asia/Seoul) 시각을 확인한다. 작성자는 사용자 지정 식별자, 확인된 요청자의 GitHub 사용자명 순으로 사용하며 없으면 질문한다. package.json author·Git user.name·저장소 소유자를 확인 없이 현재 작성자로 사용하지 않는다.
- 이름 충돌은 생성 직전에 확인하고 필요하면 짧은 식별자를 추가한다. 생성 후에는 이름을 유지하며, 같은 기능을 이어 갈 때는 관련 계획을 재사용한다.
- 작업 시작·재개 시 사용자가 지정한 계획과 실제 코드·미완료 변경을 확인한다. 관련 계획이 여럿이면 최신 파일이라는 이유만으로 임의 선택하지 않고 작업 내용과 대조한다.
- 승인된 작업의 진행 상태·검증 근거·미검증 범위·남은 작업을 해당 계획에 반영한다. 범위 변경 시 수정안을 제시하고 추가 승인 필요성을 확인한다.
- 체크 표시나 계획 파일의 승인 문구만으로 새로운 권한을 얻었다고 판단하지 않는다. 특히 실제 DB 변경·배포·Git 작업은 확인된 승인 범위를 따른다. 계획 파일 생성 승인을 구현 승인으로 확대 해석하지 않는다.
- 비밀값이나 실제 개인정보를 계획에 기록하지 않는다. GitHub 협업 시에는 [계획 파일 협업](collaboration.md#계획-파일-협업)도 확인한다.

## 유지보수와 관심사 분리

- 모든 코드 작업의 시작과 완료 전에 변경 대상의 관심사 분리 필요성을 검토한다. 시작할 때는 기존 책임과 영향 범위를, 완료 전에는 변경으로 책임이 과도하게 섞였는지 확인한다.

### 관심사 분리

- 화면 표시, 입력 검증, DB 접근, 외부 서비스 호출 등 서로 다른 책임이 한 파일이나 함수에 과도하게 섞여 있는지 확인한다.
- 서로 다른 이유로 자주 변경되는 코드가 결합되어 있는지 확인하고, 역할과 변경 이유에 따라 분리할 이점을 검토한다.
- 구체적인 화면·서버·DB 기준은 [프론트엔드 지침](frontend.md), [서버 지침](server.md), [DB 지침](database.md)을 필요한 범위에서 함께 적용한다.

### 중복 방지(DRY)

- 같은 업무 규칙·검증 규칙·처리 로직을 여러 곳에서 관리해 수정 누락이나 동작 불일치가 생길 수 있는지 검토한다. 새로 만들기 전에 기존 구현의 재사용 가능성을 확인한다.
- 같은 책임과 규칙으로 함께 변경되어야 하는 부분은 공통화를 검토한다. 모양이나 코드가 비슷하다는 이유만으로 역할·변경 이유가 다른 부분을 억지로 합치지 않는다.
- 공통화할 때 호출하는 화면·서버의 영향과 Server·Client 경계, 기존 동작·응답 형식을 확인한다. 공유할 수 있는 입력 규칙과 서버 전용 권한·업무 검사는 구분한다.

### 과도한 설계 방지와 변경 승인

- 기존 구조와 프로젝트 규모를 우선하며, 책임이 명확한 짧은 코드는 유지한다. 단순히 파일을 작게 만들기 위한 분리나 불필요한 계층·폴더 추가는 하지 않는다.
- 분리·공통화로 얻는 이점과 이해·수정 비용을 비교한다. 아직 필요하지 않은 재사용을 가정해 범용 구조를 미리 만들지 않는다.
- 개선이 필요하면 비개발자가 이해할 수 있도록 현재 문제, 분리·공유할 책임, 대상 파일, 영향 범위와 수정안·검증 방법을 설명한다.
- 검토만으로 파일 이동·분리·리팩토링을 실행하지 않는다. 기존 승인 범위에 포함되지 않는 구조 변경은 별도로 제안하고 승인 후 적용한다.

## Next.js와 TypeScript

- `src/app/`의 App Router 구조와 `src/`를 가리키는 `@/` 별칭을 유지한다.
- 기본적으로 Server Component를 사용하고 브라우저 API, 이벤트, React Hook이 필요한 부분만 Client Component로 만든다.
- Client Component에 서버 전용 모듈을 import하지 않는다. Server Component에서 전달하는 값의 직렬화 가능성을 확인한다.
- TypeScript strict를 유지하고 불필요한 `any`, 강제 타입 단언, 중복 타입을 피한다.
- 기존 UI·API 응답 형식·데이터 처리 방식을 요청 없이 변경하지 않는다.
- 불필요한 전역 상태 라이브러리와 외부 HTTP 라이브러리를 추가하지 않는다.

## 적용 상태와 검증 범위 보고

- 결과를 기능·변경 대상별로 지침만 제공 / 코드 구현 / 로컬 검증 / DB 검증 / 배포 검증으로 구분한다. 하나의 단계로 전체 상태를 뭉뚱그리지 않으며 해당 없음·미실행·실패와 이유도 표시한다.
- 지침·문서·계획 작성이나 패키지 설치만으로 기능 구현이 끝났다고 말하지 않는다. 스키마 파일 작성·Client 생성·실제 DB 적용, 빌드·배포·배포 주소에서의 기능 검증도 각각 구분한다.
- 로컬 검증에는 타입·린트·서식·빌드·HTTP·브라우저 중 실제 수행한 검사와 결과를 적는다. DB 검증에는 읽기 전용 연결·업무 조회·쓰기·권한 검사를, 배포 검증에는 실제 배포 여부·환경·대상 코드·확인한 기능을 구분한다. 검사 결과를 다른 환경이나 기능으로 확대하지 않는다.
- 관련 계획을 사용하는 승인된 작업에서는 [최신 상태 양식](../plans/README.md#기본-양식)에 근거·미검증 범위·남은 작업을 기록한다. 계획이 없으면 결과 보고에 같은 구분을 사용한다. 문서 수정만 한 작업에는 불필요한 앱·DB·배포 검사를 요구하지 않는다.

## 검증

- 변경 파일 확인 후 `npm run check`를 실행하고 실행 코드·설정 변경이면 `npm run build`를 확인한다.
- npm run check도 typecheck 과정에서 Prisma Client·Next.js 타입·TypeScript 증분 파일 등을 생성·갱신할 수 있음을 설명한다. 직접 작성한 소스·실제 DB 변경과 자동 생성물 갱신을 구분하고, 생성물은 Git 제외 규칙을 유지한다.
- DB 스키마를 수정했다면 `npm run db:validate`도 실행한다.
- 기능에 맞춰 오류·빈 데이터·입력 경계·주요 동작을 확인한다. 중요한 로직에는 필요한 테스트 구성을 제안한다.
- 현재 테스트 실행 명령이 없으므로 `npm test`가 있다고 가정하지 않는다.
- 검사 실패와 미검증 항목을 구분하여 보고한다.
- 코드 검토·자동 검사·HTTP 응답 확인·브라우저 동작·시각적 배치 검증을 구분한다. HTTP 성공만으로 모바일·다크 모드·키보드 조작·화면 배치 검증이 완료됐다고 보고하지 않는다.
