# 프론트엔드 지침

화면·스타일·폰트·공통 UI·폼 사용성과 접근성 작업에 적용한다.
공통 승인 규칙은 [AGENTS.md](../AGENTS.md), 개발 순서·계획·관심사 분리·공통 검증은 [개발 지침](development.md)을 함께 따른다.

서버 처리·입력 검증·인증·캐시에 연결되는 화면은 [서버 지침](server.md)도 읽는다. 오류 분석은 [오류 추적 지침](troubleshooting.md)을 함께 적용한다.

## UI/UX와 KRDS 참고 기준

- 화면 계획·구현·개선 시 [UI/UX 안내](../docs/UI_UX.md)를 참고해 사용자 역할·핵심 과업·다음 행동·정보 구조·필요한 상태를 정한다. 단순 문구 변경이나 화면과 무관한 작업에 전체 설계 절차를 강제하지 않는다.
- 기존 디자인·계획과 KRDS 참고 여부를 확인한다. 일반 서비스는 관련 원칙·스타일·컴포넌트·패턴을 선택적으로 참고하고, 공공 프로젝트는 발주·기관 요구와 공식 적용 기준을 확인해 범위를 제안한다. 기존에 합의한 같은 범위는 반복해서 묻지 않는다.
- 선택한 요소는 공식 [KRDS](https://www.krds.go.kr/)에서 실제 가이드·버전·적용 항목을 확인한다. 접근할 수 없으면 한계를 밝히고 구체 수치를 추측하지 않는다. 관련 계획에는 참고 URL·버전 또는 확인 기준, 적용·제외 항목과 이유를 기록한다.
- 정부 공식 배너·기관 식별 요소를 일반 서비스에 임의로 사용하지 않는다. 리소스 복사 시 개별 이용·저작권 조건을 확인하고, KRDS 참고를 이유로 폰트·라이브러리·전체 스타일을 자동 설치하거나 기존 UI를 일괄 교체하지 않는다. Next.js·Tailwind와 기존 컴포넌트를 우선 활용한다.
- 메뉴·용어·버튼 우선순위·색상·간격의 일관성, 로딩·성공·오류·빈 결과·접근 제한, 입력 손실·중복 제출·중요 작업의 확인·복구를 검토한다. 불필요한 확인창을 모든 행동에 추가하지 않는다.
- 의미 있는 HTML·라벨·대체 텍스트·키보드 순서·포커스 이동과 복귀·색 대비·색 외의 정보 전달·확대·모바일 조작을 확인한다. 모달·메뉴 등은 모양뿐 아니라 실제 동작을 검증하고 ARIA만 추가해 접근성이 완성됐다고 판단하지 않는다.
- 주요 사용자 흐름과 필요한 상태를 실제 브라우저에서 검증한다. 코드·HTTP 확인과 시각적 배치·키보드·모바일 검증을 구분하고 접근하지 못한 환경은 미검증으로 남긴다. 공식 기준과 자체 권고를 구분하며 검증 없이 KRDS 전체 준수·웹 접근성 인증 완료로 표현하지 않는다.

## 화면 설계와 폰트 선택

- 화면을 처음 설계하거나 폰트 변경 요청을 받으면 기존 코드·계획의 선택을 확인하고 [폰트 선택 안내](../docs/FONTS.md)를 참고한다. 기본 설정으로 시작할 수 있음을 설명하고, 한글 디자인·브랜드 요구·외부 다운로드 제한 등 필요가 있을 때 후보와 로딩 방식을 제안한다.
- 이미 결정한 폰트는 유지하며 동일 범위에서 반복해서 묻지 않는다. DB·서버만 수정하거나 폰트와 무관한 단순 작업에는 선택을 요구하지 않는다.
- 무료 폰트는 공식 출처에서 상업적 이용·웹 임베딩·파일 재배포·수정 조건과 필요한 고지를 확인한다. 무료 다운로드만으로 모든 사용이 허용된다고 판단하지 않는다. 확인한 출처·사용 버전·라이선스와 한글 지원·필요 굵기·용량을 제안에 포함한다.
- next/font/google의 개발·빌드 시 외부 다운로드와 배포 후 자체 제공, next/font/local의 파일 포함, 시스템 폰트의 환경별 표시 차이를 구분한다. 실제 CSS의 font-family·Tailwind 클래스 적용도 확인하고 import만으로 화면 전체에 적용되었다고 판단하지 않는다.
- 선택 결과는 관련 계획을 사용하는 승인된 작업에서 기록한다. 파일 다운로드·추가·설정 변경은 승인 범위에서 수행하고, 폰트 파일을 포함하면 원본 저작권·라이선스 고지도 보존한다. 프로젝트의 MIT 라이선스로 외부 폰트 라이선스를 대체하지 않는다.
- 변경 후 한글·영문·숫자·필요 굵기, 대체 글꼴·모바일 줄바꿈·레이아웃 변화와 빌드를 확인한다. 외부 다운로드 제거가 목적이면 사용하지 않는 원격 폰트 import도 검토하고 실제 확인 결과와 미검증 범위를 구분한다.

## 아토믹 디자인의 선택적 적용

- 화면 구현·개선 시 작은 UI 요소를 조합하는 관점으로 재사용과 관심사 분리 필요성을 검토한다. 아토믹 디자인의 모든 계층을 의무적으로 적용하지 않는다.
- 같은 책임·동작·디자인으로 반복되거나 공통 변경의 이점이 분명한 버튼·입력창·폼·화면 영역은 공통 컴포넌트로 분리할지 검토한다. 모양만 비슷하고 역할이 다른 UI를 억지로 하나로 합치지 않는다.
- 작은 요소 → 조합된 UI → 화면의 관계로 책임을 구분하되, 한 번 사용하는 단순 UI는 해당 화면에 유지할 수 있다. 현재 시작 안내 화면도 이 지침을 추가했다는 이유만으로 분리하지 않는다.
- atoms·molecules·organisms·templates·pages 폴더를 처음부터 모두 만들지 않는다. 필요할 때 기존 구조에 맞는 최소한의 컴포넌트 파일·폴더만 제안한다.
- 작은 표시용 컴포넌트에 DB 접근·권한 판정·복잡한 업무 규칙을 섞지 않는다. 아토믹 디자인을 백엔드 계층 설계나 보안 검증의 대체 기준으로 사용하지 않는다.
- Next.js App Router의 화면 진입점은 src/app/에 유지한다. 아토믹 디자인의 pages라는 개념 때문에 src/pages/를 새로 만들지 않는다. Server·Client Component 경계를 불필요하게 넓히지 않는다.
- 공통 컴포넌트 변경이 영향을 주는 화면과 로딩·오류·빈 상태·모바일·키보드 사용을 함께 확인한다. 분리의 이점보다 이해·수정 비용이 크면 현재 구조를 유지한다.
- 분리·이동이 필요하면 이유, 대상, 재사용 범위와 영향을 쉬운 말로 설명하고 승인된 범위에서 적용한다. 기존 승인 범위 밖의 구조 변경은 별도 승인 후 진행한다.

사용자 설명과 요청 예시는 [화면 재사용 안내](../docs/CODEX_GUIDE.md#화면-재사용과-아토믹-디자인-선택-사항)를 참고한다.

## 폼 사용성과 접근성

- 폼이 필요하면 React Hook Form, Zod, `@hookform/resolvers`를 우선 활용한다.
- label, 오류 메시지 연결, 키보드 조작, 제출 중 표시와 중복 제출 방지를 고려한다.
- 서버 입력·업무·권한 검사는 [서버 유효성 검사 기준](server.md#화면서버-유효성-검사)을 따르고, 서버의 안전한 오류 결과를 필드별·폼 전체 안내로 연결한다.
