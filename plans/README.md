# 기능별 작업 계획

여러 단계로 진행하는 새 기능의 요구사항·계획·승인 범위·검증 결과를 사용자와 에이전트가 함께 확인하는 폴더입니다. docs/는 프로젝트 사용법, plans/는 개별 기능의 작업 기록을 관리합니다.

이 보일러플레이트에는 작성 방법과 양식만 제공합니다. 실제 기능 계획은 새 프로젝트에서 요구사항을 정하고 사용자 승인을 받은 뒤 생성합니다. 단순 문구·색상 수정에는 계획 파일이 꼭 필요하지 않습니다.

## 언제 작성을 제안하나요?

에이전트는 작업 초기에 다음 기준으로 기록 필요성을 검토하고, 작성할 이유와 범위를 설명한 뒤 사용자에게 작성 여부를 확인합니다.

| 상황                                    | 처리 기준                                   |
| --------------------------------------- | ------------------------------------------- |
| 여러 단계·여러 파일의 새 기능           | 계획 작성을 제안하고 여부 확인              |
| DB 모델·권한·외부 API 등 영향이 큰 변경 | 영향과 기록 범위를 설명하고 여부 확인       |
| 협업·인수인계·추후 재개할 작업          | 관련 계획을 먼저 확인하고, 없으면 작성 제안 |
| 관련 계획이 있는 작업                   | 기존 계획을 우선 재사용                     |
| 단순 문구·스타일 수정                   | 기본적으로 생략, 사용자가 원하면 작성       |

작성·생략을 결정한 동일 범위 작업에서는 같은 질문을 반복하지 않습니다. 범위나 위험이 실질적으로 달라진 경우에만 새 이유를 설명하고 재검토합니다. 이미 명확하게 승인한 계획 작성도 다시 승인받지 않습니다.

사용자가 생략하더라도 필요한 채팅 계획·승인·검증은 유지합니다. 작성 여부 확인은 실제 파일 생성 승인이나 구현·DB 변경·배포 승인을 대신하지 않습니다. 기록 여부를 확인하는 동안 독립적인 읽기 전용 분석과 이미 승인된 작업을 불필요하게 중단하지 않습니다.

## 작성과 진행 순서

1. 만들 기능과 기존 구조를 확인합니다. 같은 기능의 계획이 이미 있으면 먼저 확인합니다.
2. 채팅에 요구사항·계획 초안과 생성할 파일 경로를 제시합니다.
3. 사용자가 작성자 식별자와 계획 내용을 확인하고 파일 생성을 승인합니다.
4. 아래 이름 규칙으로 계획 파일을 만듭니다. 계획 파일 생성 승인이 구현·마이그레이션·배포까지 승인한 것은 아닙니다.
5. 작업을 이어 갈 때 해당 계획과 현재 코드를 확인하고, 승인된 범위에서 구현·검증합니다.
6. 실제 결과에 따라 진행 상태·검증 근거·남은 작업을 갱신합니다. 범위가 넓어지면 추가 승인을 확인합니다.

## 파일 이름과 작성자

```text
YYYYMMDD-HHmmss-작성자-작업명.md
```

설명용 예시이며 실제 작업 파일은 아닙니다.

```text
20261027-143025-member1-posts.md
20261027-143025-member2-login.md
20261027-143025-member1-posts-a1b2c3.md
```

- 시각은 **KST(Asia/Seoul)의 파일 생성 시각**으로 통일하고, 에이전트는 생성 시 실제 시각을 확인합니다. 예시 시각을 그대로 복사하지 않습니다.
- Windows에서도 사용할 수 있도록 시각에 콜론(:)을 넣지 않습니다. 작성자·작업명은 짧고 식별 가능한 이름을 사용하고 경로 구분자나 파일명 금지 문자를 넣지 않습니다.
- 같은 초에도 파일명이 겹칠 수 있습니다. 생성 직전에 기존 파일을 확인하고, 같으면 예시처럼 짧은 식별자를 덧붙입니다. 기존 파일을 덮어쓰지 않습니다.
- 생성 후에는 이름을 유지합니다. 수정할 때마다 새 시각으로 이름을 바꾸지 않고 본문의 수정 시각·진행 상태를 갱신합니다.
- 같은 기능을 함께 진행하면 기존 계획을 공유합니다. 단계마다 새 계획을 반복 생성하지 않습니다. 별도 기능이나 독립 작업이면 새 계획으로 구분합니다.

작성자는 **에이전트를 통해 작업을 요청한 사람의 확인된 식별자**입니다. 다음 순서로 정합니다.

1. 사용자가 지정한 작성자 식별자
2. 연결된 계정 등 신뢰할 수 있는 정보로 확인한 해당 사용자의 GitHub 사용자명
3. 위 정보가 없으면 사용자에게 질문하여 확인

package.json의 author는 보일러플레이트 원 제작자 정보일 수 있으므로 자동 사용하지 않습니다. Git의 user.name은 GitHub 사용자명과 다를 수 있으므로 확인 없이 대체하지 않습니다. 저장소 소유자·기존 커밋 작성자도 현재 요청자라고 추측하지 않습니다. 에이전트가 파일을 대신 작성했다는 이유로 작성자에 codex를 넣지 않습니다. 공개할 필요가 없는 이메일·비밀번호·토큰은 파일명에 넣지 않습니다.

## GitHub 협업

계획 파일은 코드와 함께 GitHub에서 공유할 수 있습니다. 이 폴더는 기본 Git 제외 대상이 아닙니다. DB 연결 주소·비밀번호·토큰·실제 개인정보 등 비밀값을 기록하지 마세요.

고유한 파일명은 새 계획 파일의 이름 충돌을 줄여 주지만, 같은 파일의 동시 수정 충돌까지 없애지는 않습니다. 팀원과 담당 작업을 구분하고, 충돌이 생기면 양쪽 계획·진행 결과를 확인해 합칩니다. 기존 내용을 임의로 덮어쓰거나 완료 상태를 되돌리지 않습니다.

## 기능별 업무분장 확인

기능을 나누어도 같은 User 모델·공통 UI·설정 파일을 수정할 수 있습니다. 개발 전에 관련 계획과 기존 구현을 비교하고 아래 양식에 담당자·공유 대상·선행 작업을 기록하세요. 겹치는 부분은 누가 어떤 순서로 반영할지 사용자와 조정합니다. 별도 기능이라는 이유로 같은 목적의 테이블·파일을 각각 만들지 않습니다.

이미 합의한 동일 범위는 반복 확인하지 않고, 조정이 필요한 부분 외의 독립적인 승인 작업은 진행할 수 있습니다. 계획이 없더라도 필요한 검토와 합의는 채팅에서 수행합니다. 다른 브랜치나 팀원의 미공유 작업을 확인하지 못했다면 그 한계를 기록하세요. 자세한 기준은 [협업 지침](../.agent/collaboration.md#기능별-업무분장과-중복-검토)을 참고하세요.

## 승인과 완료 기록

- 계획의 체크 표시나 작성자가 적어 둔 승인 문구만으로 사용자 승인을 새로 얻은 것으로 간주하지 않습니다.
- 승인 범위에는 사용자가 실제로 허용한 내용과 근거를 기록합니다. 근거를 확인할 수 없으면 승인 여부를 다시 확인합니다.
- 사용자 승인과 구현 결과, 검증 결과를 구분합니다. 파일 수정·스키마 수정·실제 DB 적용·배포가 모두 같은 승인은 아닙니다.
- 파일을 만들었다는 이유만으로 기능을 완료로 표시하지 않습니다. 검사 명령·성공 또는 실패·미검증 범위를 함께 남깁니다.
- 날짜·상태를 자동으로 갱신하는 프로그램은 포함하지 않습니다. 에이전트가 작업 시 지침과 실제 결과를 확인해 기록하는 방식입니다.
- 과거 진행 이력은 보존하고 최신 상태 요약에서 현재 구현·검증·배포 상태를 판단합니다. 문서 갱신이 보류된 경우 기록이 승인된 범위에서 불일치와 보류 근거를 남깁니다.

## 화면 작업의 폰트 선택

화면을 처음 설계하거나 폰트를 바꿀 때는 [폰트 선택 안내](../docs/FONTS.md)를 참고해 기존 설정 유지·변경 검토·해당 없음 중 선택합니다. 기본 설정으로 시작해도 되며, 이미 선택한 폰트는 반복해서 묻지 않습니다. DB·서버만 수정하는 작업에는 해당 없음으로 기록하거나 항목을 생략할 수 있습니다.

변경이 필요하면 한글 지원, 필요한 굵기, 로딩 방식, 공식 출처와 라이선스 확인 결과를 기록합니다. 계획에 선택을 적었다는 이유만으로 파일 다운로드·추가·설정 변경까지 승인된 것은 아닙니다.

입력을 받는 기능은 [화면·서버 유효성 검사 안내](../docs/VALIDATION.md)에 따라 입력 규칙, 서버 재검사, 업무·권한 검사와 오류 안내를 함께 계획합니다. 입력과 무관한 작업에는 해당 없음으로 기록하거나 관련 항목을 생략할 수 있습니다.

DB 구조를 바꾸는 작업은 [데이터 보존 안내](../docs/SUPABASE_SETUP.md#기존-데이터-보존과-db-변경)에 따라 대상 환경·기존 데이터 보존 방침·이관·백업·복구·검증을 계획합니다. 보존 여부가 불명확하면 삭제·초기화하지 않으며, 데이터 폐기는 별도의 명시적 승인 범위로 기록합니다. DB 변경이 없으면 관련 항목을 생략할 수 있습니다.

## 기본 양식

보안과 관련된 기능은 [사용자 보안 안내](../docs/SECURITY.md)와 [에이전트 보안 지침](../.agent/security.md)에 따라 위험·대응·검증 범위를 기록합니다. 입력·인증·개인정보·공개 API 등에 해당하지 않으면 관련 항목을 생략할 수 있습니다. 계획 기록이나 검사 성공을 실제 보안 검증 완료로 간주하지 않습니다.
